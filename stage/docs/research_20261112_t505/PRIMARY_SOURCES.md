# T505 retention pilot: primary-source review

Date: 2026-11-12. Scope: Stage only; literature and protocol recommendation, no implementation, native rollout, optimizer update, or change to T504 evidence. The T505 label denotes a proposed independent bounded pilot, not a launched or accepted experiment. Full primary PDFs were consulted at the sections identified below; this is not a claim to have read every appendix or all historical chats.

## Decision supported by the sources

Use simultaneous old/new successful-history supervision with a per-task native acceptance guard on an explicitly unpromoted research copy. The guard should decide whether a complete proposed Actor+Adam block survives; surrogate losses should guide proposals. This is a practical inference from the mismatch between memory-loss constraints and the desired closed-loop success predicate, not a theorem or a demonstrated causal advantage of hard guards. GEM, A-GEM, and PCGrad offer relevant alternatives for later controlled comparison; none establishes that a finite neural-policy update preserves these Stage task IDs in native execution.

## Application to the proposed bounded pilot

The following project state is supplied by the coordinating task and must be checked against final T504 artifacts before registration: T503 retained old8=8/8 and field24=6/24. T504 currently shows field24=7/24, with the original six field successes retained, but old8=6/8: `dev_task6_13` CONTACT and `dev_task7_13` TIMEOUT. T504 is still finishing native verification/audit/backup; these numbers are provisional here, and this note does not change its status or files. Read the final report before choosing exact input hashes.

Recommendation, conditional on verified T504 completion:

1. Start a separate, explicitly unpromoted T504 research copy; preserve the independent T503 original/best model and all failure evidence. Select the two corresponding **actual successful T503 complete histories** as repair targets. Do not label failed T504 executions as successful targets or assume every old historical trace succeeds under T504.
2. Jointly train repair and retention objectives: keep the thirteen actual T504 successes (old six plus field seven), while matching the two lost old tasks' successful T503 histories. Preserve original observations, recurrent history, executed actions, and the established action-density semantics. This combines behavior cloning of successful actions with functional retention; it is not fresh on-policy RL or a new causal mechanism.
3. Predeclare at most four blocks of sixteen optimizer steps, with fixed data, weights, sampling, and learning rate. After each proposed block, evaluate all fifteen task IDs from their real native starts. The thirteen existing successes are protected immediately; whenever a repaired task is accepted as successful it joins the protected set. Acceptance must check ID membership, not only a success count. Reject the entire proposed Actor **and Adam state** if any currently protected ID loses the original success predicate. Two consecutive block rejections stop learning; no fallback grid, extended budget, or new launch is implied.
4. A two-task repair improvement is an empirical pilot success only when the same accepted candidate satisfies all fifteen native tasks. Partial repair should be reported explicitly. Record CONTACT, TIMEOUT, invalid, and censored outcomes separately; missing tests are not passes. The guard evaluates block endpoints, so it does not promise all intermediate optimizer states succeed.
5. Final acceptance must still run the full 32 distinct cases (old8 plus field24), with 24 exact field replays as the specified reproducibility check. Exact replays are not independent new samples. The fifteen development checks influence selection and cannot be presented as untouched holdout evidence. Keep old/new per-ID outcomes and complete denominators alongside totals; do not infer full old275, wider-distance, or unseen-start retention from this finite panel.

## What a hard native guard adds—and what it cannot establish

For the exact protected starts, simulator configuration, termination rules, and checked accepted block endpoints, the guard directly measures the desired success predicate and rejects a measured loss. This can catch finite-step nonlinear and trajectory-distribution failures that stored-history NLL, local KL, GEM constraints, pooled A-GEM gradients, or PCGrad conflict removal need not expose. Joint replay also gives the update a positive repair signal; a guard alone cannot create a useful direction.

This is an engineering rationale, not evidence that hard guards learn more efficiently or generalize better than gradient regularization. Guards can reject useful progress, stall with incompatible objectives, consume native budget, and overfit a finite development panel. A causal comparison would require a separately registered same-initialization, same-data, same-budget control varying only the guard or gradient method. This proposal changes several ingredients relative to T504 and cannot isolate any one ingredient's effect. No global safety, stability, monotonic unseen-task improvement, algorithmic novelty, or completed repair claim follows from the literature or this note.

## Registration decision after the review

The coordinating agent subsequently verified T504 COMPLETE, audit PASS, all 61 archived members fully read back with SHA verification, all native/finalizer processes stopped: 49 actual supervised Adam steps, field7/24, old8=6/8, rejected with whole-experiment rollback; original T503 remains the accepted model. T505 will explicitly use the rejected candidate only as an unpromoted research initialization for a distinct joint repair objective.

The final protocol tightens the suggested stop rule to **the first rejected block**. With fixed data and full Actor+Adam rollback, blindly repeating the same deterministic block would reproduce the same candidate; no such duplicate is authorized. Fifteen guard cases are already measured on the same final candidate; if all old8 are restored, only the other 17 field cases are new native tests, then all 24 field cases get exact replays. Thus there are 32 distinct final cases, with the final seven field guard cases explicitly reused, not 32 additional independent tests. The registered plan, not the earlier recommendation, controls execution. No GEM/A-GEM/PCGrad code or guarantee is claimed.
